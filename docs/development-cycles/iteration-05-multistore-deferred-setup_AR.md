# الدورة الخامسة: تعدد الفروع والوحدات المؤجلة والأثر المحاسبي

تستكمل هذه الدورة مبدأ **«الهيكل التنظيمي أولاً»** عبر معالجة الفجوات التي لا تظهر في تهيئة متجر واحد فقط. أصبح سياق المنشأة العام مرجع الإطلاق المشترك، بينما يستطيع كل مستخدم مخول اختيار سياق فرعه الشخصي أو الرجوع إلى سياق المنشأة. كما لا يؤدي اختيار وحدة جديدة لاحقاً إلى إعادة حجب نظام يعمل بالفعل؛ تبقى الوحدة الجديدة غير مرئية وغير قابلة للوصول حتى تكتمل جاهزيتها التنظيمية والتشغيلية.

> **قاعدة الحجب النهائية:** لا تعني الوحدة المحددة أنها وحدة عاملة. لا تصبح الوحدة مرئية أو قابلة للوصول إلا بعد التفعيل الخلفي الناجح، ويظل حارس الصلاحيات وحارس جاهزية الوحدة مرجع القرار النهائي.

## التغييرات المنجزة

| المجال | التحسين | الضمان التشغيلي |
|---|---|---|
| سياقات التشغيل | أضيفت قائمة للسياقات الجاهزة للمستخدم، وتدعم اختيار السياق الشخصي أو سياق المنشأة العام. | يستطيع مستخدم ثانٍ العمل على متجر أعده مسؤول مختلف؛ ولا تتسرّب سياقات مستخدم آخر الخاصة. |
| تعدد الفروع | ربطت الواجهة محدد متجر التشغيل بمخزن حالة موحد ونقطة نهاية محكومة. | يمكن تبديل الفرع دون تمرير معرفات مستودع أو نقطة بيع غير موثوقة من العميل. |
| الإطلاق المؤجل | فُصل `setup_required`، الذي يحجب الإطلاق الأولي فقط، عن `pending_module_setup`، الذي يصف وحدة مؤجلة. | تبقى المبيعات والوحدات النشطة متاحة عند إضافة وحدة جديدة لم يكتمل إعدادها بعد. |
| رحلة الإكمال | أضيف مسار `/setup?continue=1` وإجراء واضح من بطاقة الجاهزية لإضافة وحدة لاحقة. | يعيد المستخدم استخدام الرحلة الموجهة نفسها، من دون إرباكه ببوابة تثبيت أولي زائفة. |
| واجهة الهيكل | أضيف وضع تهيئة صريح لتبويب العقد: محرر أولي عند غياب العقد، وجدول مبسط عند وجودها. | لا تظهر أدوات البحث والفلترة والتعديل الجماعي والحذف ضمن مسار التهيئة الموجه. |
| المحاسبة | تمرر خدمة البيع مركز التكلفة ومركز الربح من سياق التشغيل الموثوق إلى كل سطر قيد. | تتطابق قيود الذمم والإيراد والضريبة والنقدية وتكلفة البضاعة والمخزون مع أبعاد الفرع المحاسبية. |
| RBAC | أزيل وصول دور المحاسب القياسي إلى وحدة المبيعات، وأضيف ترحيل للمنشآت القائمة. | يسبق رفض الصلاحية `403` فحص الجاهزية؛ ولا يحصل المستخدم غير المخول على كشف لحالة تشغيل الوحدة. |

## محاكاة السيناريوهات

اختبرت الدورة الحالات التي تشكل الحدود العملية لنموذج منشأة متعددة الفروع. شمل ذلك انتقال مستخدم جديد إلى سياق منشأة عام، وتبديل مستخدم واحد بين سياقين شخصيين ثم العودة إلى السياق العام، وإضافة وحدة مؤجلة بعد وجود مبيعات عاملة، وحالة محاسب لا يملك صلاحية المبيعات.

| السيناريو | النتيجة المتحققة | الاختبار الحارس |
|---|---|---|
| مسؤول يجهز المتجر ثم مستخدم ثانٍ يعمل عليه | يحل المستخدم الثاني سياق المنشأة العام تلقائياً عند غياب سياق شخصي. | `SalesExecutionContextResolverTest` |
| مستخدم متعدد الفروع | تعرض واجهة الخلفية السياقات الشخصية إضافة إلى سياق المنشأة العام، ويبدل الاختيار الافتراضي بأمان. | `OperatingContextApiTest` |
| منشأة تعمل ثم تختار وحدة جديدة | تبقى `setup_required=false`، وتصبح `pending_module_setup=true` والوحدة الجديدة معلقة فقط. | `SetupStateApiTest` |
| مستخدم مخول مع وحدة مبيعات غير مفعلة | يرفض الوصول بـ`423 MODULE_NOT_OPERATIONAL`. | `ModuleOperationalAccessTest` |
| محاسب قياسي مع وحدة مبيعات مفعلة | يرفض الوصول بـ`403` بسبب RBAC، قبل فحص الجاهزية. | `ModuleOperationalAccessTest` |
| فاتورة ضريبية مرتبطة بمتجر | تحمل الفاتورة وكل سطور دفتر الأستاذ مركزي التكلفة والربح من سياق المتجر. | `TaxEngineIntegrationTest` |

## تنظيم الواجهة

تم فصل بطاقة جاهزية متجر التشغيل في ملفات مستقلة للبنية والمحتوى والتنسيق. يبقي هذا الفصل الصفحة التنظيمية مسؤولة عن تنسيق الحالة والعمليات فقط، بينما يضع نصوص البطاقة ومفاتيحها في ملف محتوى، وأنماطها في CSS Module. كما يعاد استخدام `Button` و`SearchableSelect` و`Table` و`ActionButtons` من مكتبة الواجهة القائمة؛ لم تُنشأ بدائل تصميمية موازية.

## نتائج التحقق

| أمر التحقق | النتيجة |
|---|---|
| مجموعة اختبارات Laravel الكاملة | نجحت: **1,159 assertion**. ظهرت **416 تحذيراً** خاصاً بتحميل ملفات الترجمة في بيئة الاختبار، من دون إخفاقات. |
| اختبارات السياق والتفعيل والمبيعات والضريبة | نجحت اختبارات السياق العام وتبديل الفروع والوحدة المؤجلة وحارس RBAC والأبعاد المحاسبية. |
| فحص تنسيق الخلفية | نجح `Pint` للملفات المعدلة. |
| فحص TypeScript | نجح `pnpm exec tsc --noEmit`. |
| بناء الواجهة | نجح `pnpm build`، ثم حُذفت ملفات مساحة العمل المؤقتة قبل الالتزام. |

## ملاحظات التسليم

يبقى مسار التهيئة الأولية صارماً: لا يعرض النظام التشغيلي قبل اختيار نطاق الوحدات وإنشاء البنية والسياق العام وتفعيل الوحدات الجاهزة. وبعد الإطلاق، تتغير طبيعة العملية من حجب للنظام إلى **توسع محكوم**: يختار المستخدم وحدة إضافية، تستمر الوحدات النشطة بالعمل، ولا تظهر الوحدة الجديدة إلا عند اجتياز التحقق الخلفي نفسه.
