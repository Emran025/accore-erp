# الدورة الثانية: تنفيذ تهيئة «الهيكل أولاً»

**الحالة:** مكتمل تقنياً ضمن نطاق التهيئة التنظيمية، إتاحة الوحدات، وسياق البيع.  
**الفرع:** `agent/retail-setup-hardening`.

## النتيجة التشغيلية

أصبح المسار التشغيلي للتثبيت الجديد محكوماً بالترتيب التالي: يختار المسؤول الوحدات، فتسجل كـ **محددة** لا كمفعلة. بعد ذلك ينتقل إلى واجهة الهيكل التنظيمي القائمة في وضع تهيئة بلا القائمة الجانبية. لا يمكن لوحدة المبيعات أو الوحدات التشغيلية المماثلة أن تصبح مفعلة إلا بعد وجود عقدة تنظيمية نشطة، وموقع تشغيل جاهز يربط العقدة بالمستودع وPOS ومركز التكلفة ومركز الربح. عند التفعيل الناجح فقط تظهر الوحدة وتسمح واجهاتها الخلفية بالوصول.

| مرحلة القرار | مصدر الحقيقة | السلوك المطبق |
| --- | --- | --- |
| اختيار الوحدة | `settings.setup.selected_modules` | حفظ نية المستخدم؛ لا تغيير لـ`modules.is_active`. |
| التحقق التنظيمي | `structure_nodes` و`operating_contexts` والعلاقات التشغيلية | يرفض العقدة غير الموجودة أو غير النشطة، وعدم اتساق المستودع وPOS مع الفرع والمراكز. |
| التفعيل | `ModuleActivationService` | يفعّل فقط الوحدات المختارة والمكتملة الجاهزية في لحظة التنفيذ. |
| الإتاحة الخلفية | `EnsureModuleOperational` | يعيد `423 MODULE_NOT_OPERATIONAL` للوحدة غير المفعلة مهما كان الرابط أو صلاحية المستخدم. |
| الإتاحة الأمامية | `MainLayout` و`/setup` | يمنع رسم الغلاف الطبيعي عند التثبيت الجديد أو عند تعذر قراءة حالة التهيئة. |

## تعديلات البناء الرئيسة

تمت إضافة `ModuleAvailabilityService` و`ModuleActivationService` و`EnsureModuleOperational` و`SalesExecutionContextResolver`. وتفصل هذه الطبقات بين الاختيار، الجاهزية، والتشغيل، بدلاً من خلطها في واجهة أو في خدمة المبيعات. كما تمت إضافة حالة تهيئة عبر `/v2/setup/state` و`/v2/setup/modules` و`/v2/setup/activate-ready`، مع صفحة `/setup` تستهلكها.

تم تشديد `OperatingContextService` وطلب تهيئته: `org_node_uuid` إلزامي ويجب أن يشير إلى عقدة تنظيمية نشطة. كما أصبحت خدمة البيع تشتق معرفات المستودع وPOS ومركزي التكلفة والربح من سياق التشغيل المعتمد؛ وترفض القيم التي يرسلها العميل إذا خالفت ذلك السياق.

> **استدراك مكتشف في المحاكاة:** كان يمكن لعقدة UUID غير موجودة أن تمر إذا اتسقت حقول المستودع وPOS معها شكلياً. أضيف تحقق حي من `structure_nodes.status = active` داخل حاسم سياق البيع، مع اختبار يغطي الحالة.

## محاكاة الحالات المنفذة

| المنشأة/الحالة | النتيجة |
| --- | --- |
| تثبيت جديد بلا وحدات أعمال مفعلة | محجوب في `/setup` حتى اختيار النطاق. |
| اختيار المبيعات فقط بلا سياق متجر | تظل المبيعات معلقة؛ لا تفعل. |
| متجر بفرع فعلي ومستودع وPOS ومراكز نشطة | تفعل المبيعات ثم تسمح مساراتها بالعمل. |
| مستخدم له سياق متجر خاص وسياق افتراضي عام | يحسم السياق الخاص بالمستخدم أولاً. |
| سياق صريح ليس افتراضياً | يرفض قبل إنشاء الفاتورة. |
| فرع/عقدة غير نشطة أو غير موجودة | يرفض قبل أي أثر على الفاتورة أو المخزون أو الأستاذ العام. |
| وصول مباشر لمسار المبيعات قبل التفعيل | يرفض من الخادم برمز `423`. |
| تعذر تحميل حالة التهيئة من الواجهة | تفشل الواجهة بشكل آمن داخل `/setup` ولا تعرض النظام. |

## التحقق المنفذ

اجتازت مصفوفة التهيئة والمبيعات ذات الصلة **20 اختباراً و82 assertion**، ثم اجتازت المجموعة الكاملة بعد إصلاح اختبارات المبيعات المتأثرة بالحارس الجديد **1,113 assertion** مع بقاء ثلاثة إخفاقات قائمة خارج نطاق التهيئة الحالية:

| الاختبار المتبقي | التصنيف | القرار |
| --- | --- | --- |
| `AttendanceApiTest::employee_can_view_own_attendance` | صلاحيات الحضور، يعيد 403 | لا يُعالج ضمن دورة تهيئة المتجر؛ يحتاج مراجعة RBAC مستقلة. |
| `LeaveApiTest::employee_can_view_own_leave_requests` | صلاحيات الإجازات، يعيد 403 | لا يُعالج ضمن دورة تهيئة المتجر؛ يحتاج مراجعة RBAC مستقلة. |
| `InvoicePolicyTest::owner_can_delete_own_invoice_when_allowed` | سياسة إلغاء الفاتورة | دين قائم في Policy لا يرتبط بحارس التهيئة أو بسياق البيع. |

تم بناء الواجهة بنجاح بواسطة `pnpm build` بعد إضافة أنواع Vitest إلى `tsconfig.json`، وهو إصلاح سابق لحالة بناء الاختبارات المضمنة لا يغير منطق المنتج.

## الدورات التالية المقترحة

تبدأ الدورة التالية بإعادة ترتيب المكوّن التنظيمي نفسه في وضع التهيئة إلى خطوات أصغر: إنشاء العقدة، ربط المراكز، إنشاء المستودع وPOS، اختبار الجاهزية، ثم تفعيل الوحدات. بعد ذلك تُعمم سياسة الجاهزية ذاتها على المشتريات والموارد البشرية والتصنيع عبر سجل متطلبات لكل وحدة، مع اختبارات متعددة المستخدمين ونطاقات صلاحية على مستوى الفرع.
