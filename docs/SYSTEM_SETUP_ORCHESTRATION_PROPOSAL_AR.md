# مقترح إعادة بناء تهيئة النظام الأولى في Accore ERP

**الإصدار:** 1.0  
**المؤلف:** Manus AI  
**النطاق:** التهيئة الأولى قبل ظهور واجهة النظام، تأسيس المنشأة، الهيكل التنظيمي، اختيار الوحدات، تهيئة الوحدات، وإتاحة التنقل تدريجياً.

## القرار التنفيذي

لا ينبغي معالجة المشكلة بنقل بطاقة «جاهزية متجر التشغيل» من آخر صفحة الهيكل التنظيمي إلى شاشة أخرى. المشكلة أعمق: الواجهة الحالية تجمع بين **استوديو إدارة هيكل تنظيمي متقدم** وبين **نموذج تشغيلي أولي**، ثم تسمح بعرض غلاف النظام والقائمة الجانبية قبل أن توجد حالة خلفية موحدة تثبت أن المنشأة أصبحت جاهزة للعمل.

> **القرار المقترح:** إنشاء طبقة مستقلة باسم **منسّق تهيئة النظام** (`System Setup Orchestrator`) تكون هي المصدر الوحيد للحقيقة عن حالة الإطلاق، وتعرض واجهة `/setup` كاملة الشاشة قبل أي جزء من نظام ERP. يعاد استخدام خدمات الهيكل التنظيمي، وإعدادات المنشأة، وجاهزية سياق التشغيل الحالية من داخل هذه الطبقة، ولا يعاد بناء منطق أعمال موازٍ لها.

يتوافق هذا مع اتجاه القضايا المفتوحة: تنص قضية منسق التهيئة على أن تكون الخلفية هي مصدر الحقيقة الوحيد للحالة، وأن تكون الحالة قابلة للاستئناف ومحمية من التكرار والتنافس [1]. كما تطلب قضية الهيكل التنظيمي إعادة استخدام نطاق **Organization Governance** القائم، لا إنشاء نموذج تهيئة تنظيمي مكرر [2]. وتؤكد قضية الوحدات أن اختيارها وتفعيلها عملية خلفية محكومة، لا مجرد تفضيل لإظهار روابط القائمة [3].

| ما هو قائم اليوم | لماذا لا يحقق الهدف | البديل الملزم |
| --- | --- | --- |
| غلاف `MainLayout` يتحقق من الدخول ثم يعرض الغلاف والقائمة الجانبية، ويكتفي بإشعار عند عدم اكتمال الجاهزية. | يسمح بالدخول إلى النظام قبل انتهاء التهيئة، ويحّول الإعداد إلى تنبيه يمكن تجاوزه. [4] | حارس مسار عالمي يطلب حالة التهيئة من الخلفية؛ إذا لم تصل المنشأة إلى الإطلاق الأساسي يعيد التوجيه إلى `/setup` قبل رسم الغلاف. |
| صفحة الهيكل التنظيمي تحتوي تسعة تبويبات إدارية وبطاقة «جاهزية المتجر» مع نافذة إدخال. | يحمل المستخدم لأول مرة في مساحة توثيقية/إدارية متشعبة، ويفرض سياق مستودع ونقطة بيع حتى حين لا تكون الوحدة المختارة بحاجة إليهما. [5] | نقل الحد الأدنى الضروري إلى خطوات تهيئة سياقية، وإبقاء شاشة الهيكل الحالية مساحة إدارية متقدمة بعد الإطلاق. |
| خدمة `OperatingContextService` تتحقق من مستودع ومركز تكلفة ومركز ربح ونقطة بيع وتخزن سياقاً افتراضياً مرتبطاً بالمستخدم. | هذه جاهزية تشغيلية لوحدة تجارية/نقطة بيع، وليست حالة تثبيت عامة أو حالة منشأة؛ ربطها بالمستخدم لا يكفي لحسم جاهزية المنشأة. [6] | اعتبارها **مُتحققاً فرعياً** يُستدعى فقط عندما تتطلب الوحدات المختارة سياق تشغيل تجاري، مع إضافة حالة تهيئة على مستوى التثبيت/المنشأة. |
| التنقل الحالي ثابت ويعتمد عملياً على الصلاحيات ووحدات الشاشة. | ليس لديه مفهوم «هذه الوحدة مختارة ولكنها لم تُهيّأ بعد»، ولا يمنع الوصول المباشر إلى المسارات. [7] | قرار إتاحة مزدوج: صلاحية المستخدم **و** حالة تشغيل الوحدة من الخلفية؛ تطبق على القائمة، وبطاقات التنقل، وحارس المسار وواجهات API. |

## النتيجة التشغيلية المراد تحقيقها

عند التثبيت لأول مرة، لا تظهر لوحة التحكم ولا القائمة الجانبية ولا صفحة الهيكل التنظيمي الكاملة. يظهر بدلاً منها **مركز إطلاق المنشأة**: رحلة قصيرة واضحة، تحفظ بعد كل خطوة، تشرح سبب كل مطلب، وتسمح بالعودة الآمنة دون فقدان البيانات.

بعد تهيئة الأساس الإلزامي للمؤسسة، ينتقل المستخدم إلى نظام محدود وآمن: تظهر أدوات النواة ومركز الإطلاق فقط. وكل وحدة يختارها المستخدم تظهر في التنقل **بعد** اكتمال تهيئتها الخلفية وتحقق متطلباتها. تبقى الوحدات المختارة وغير الجاهزة داخل مركز الإطلاق، لا كروابط فارغة أو شاشات قد تفشل لاحقاً.

```mermaid
flowchart TD
    A[تثبيت جديد] --> B{هل يوجد مالك تهيئة صالح؟}
    B -- لا --> C[تسجيل مالك التهيئة بوسيلة bootstrap أحادية الاستخدام]
    B -- نعم --> D[قراءة حالة التهيئة من الخلفية]
    C --> D
    D --> E{هل أُطلق أساس المنشأة؟}
    E -- لا --> F[/setup: تهيئة كاملة الشاشة]
    F --> G[ملف المنشأة والقالب التنظيمي]
    G --> H[اختيار الوحدات وتحليل التبعيات]
    H --> I[تهيئة النواة والمتطلبات الإلزامية]
    I --> J{اجتاز التحقق؟}
    J -- لا --> F
    J -- نعم --> K[إطلاق أساسي]
    E -- نعم --> K
    K --> L[غلاف النظام: النواة + مركز الإطلاق]
    L --> M[تهيئة وحدة مختارة]
    M --> N{الوحدة provisioned وجاهزة؟}
    N -- لا --> M
    N -- نعم --> O[إظهار الوحدة في القائمة وحراسة مساراتها]
```

## رحلة المستخدم المقترحة

### 1. مرحلة تملك التثبيت

لا تصح افتراضات من نوع «أي مستخدم مسجل يستطيع الإعداد». عند عدم وجود مسؤول مصرح له، تفتح واجهة bootstrap محدودة جداً. تعرض الواجهة حالة آمنة فقط، ثم تطلب رمز تهيئة صادر من عملية النشر أو أداة التثبيت، وتنشئ أول **مالك تهيئة** وتستهلك الرمز نهائياً. يجب أن يكون المسار محدود المحاولات، مسجلاً في سجل التدقيق، وغير قابل للاستخدام بعد نجاح الإنشاء أو بعد انقضاء المهلة.

بعد وجود المسؤول، لا يُستخدم مسار bootstrap ثانية. يدخل المالك إلى `/setup` وتُحدد صلاحياته من سياسة مخصصة للتهيئة، لا من صلاحية `settings` العامة فقط.

### 2. اختيار شكل التشغيل قبل إدخال التفاصيل

الخطوة الأولى الفعلية لا تسأل عن مئات الحقول، بل تجمع قرارات ذات أثر بنيوي: نوع المنشأة، البلد/الإقليم، اللغة الأساسية، العملة والسنة المالية، وعدد الكيانات أو الفروع إن كان مدعوماً. ثم يختار المسؤول الوحدات التي يريد تشغيلها الآن، لا كل ما قد يحتاجه مستقبلاً.

يعرض الكتالوج الوحدات كبطاقات مفهومة: الفائدة، ما سيتطلبه تشغيلها، الاعتماديات التي ستضاف تلقائياً، وأي تعارض. لا يسمح زر «متابعة» بحفظ اختيار ظاهري فقط؛ ترسل الخلفية خطة متطلبات محسوبة (`setup blueprint`) بعد حل التبعيات.

| مثال لملف تشغيل | ما يفرضه مخطط التهيئة | ما لا ينبغي فرضه |
| --- | --- | --- |
| نواة + مالية | ملف المنشأة، السنة المالية، العملات، دليل الحسابات، مراكز التكلفة/الربح حين يقتضي التصميم المالي ذلك. | مستودع أو نقطة بيع. |
| نواة + مخزون | منشأة/بنية تشغيلية، مستودع أولي، وحدات قياس وسياسات مخزون حسب نطاق المنتج. | نقطة بيع إذا لم تُختر المبيعات عبر نقطة البيع. |
| نواة + مبيعات تجزئة + مخزون | الهيكل، مستودع، مراكز محاسبية مطلوبة، ونقطة بيع مرتبطة بالمستودع. | متطلبات الموارد البشرية غير المختارة. |
| نواة + موارد بشرية | وحدات تنظيمية، وظائف/مسميات عند الحاجة، وسياسات قوى عاملة الأساسية. | مركز ربح أو جهاز POS ما لم تطلبه وحدة أخرى. |

### 3. تأسيس المنشأة والهيكل التنظيمي

تستدعي هذه المرحلة خدمات Organization Governance الحالية، لكن عبر تجربة مختصرة من أربع لوحات فقط: **ملف المنشأة**، **اختيار قالب**، **تحرير الحد الأدنى المطلوب**، ثم **مراجعة وتفعيل**. لا تعرض سجل التغيير أو تحليل النطاق أو تكاملات المراكز أو أدوات السلامة التسعة في أول تشغيل؛ هذه أدوات ما بعد الإطلاق.

يبدأ الهيكل في حالة مسودة. يمكن حفظه واستكماله، لكن لا يصبح أساساً لبقية الوحدات حتى ينجح التحقق من قواعد الطوبولوجيا والسلامة وتفعيله في معاملة واضحة. بذلك لا تُنشر مسودة ناقصة بوصفها هيكل عمل فعلي، وهو متطلب صريح في القضية التنظيمية [2].

### 4. تهيئة الوحدات واحدةً واحدة

بعد اعتماد الأساس، يعرض مركز الإطلاق وحدات مختارة في قائمة مرتبة حسب التبعيات. لكل وحدة بطاقة حالة واحدة فقط، مثل «مالية: مطلوب إعداد دليل الحسابات»، أو «تجزئة: مطلوب سياق تشغيل أولي». عند فتح بطاقة، لا يرى المستخدم إلا الأسئلة المطلوبة لتلك الوحدة في هذه المرحلة.

تكون «جاهزية متجر التشغيل» خطوة **مشروطة** داخل وحدة التجارة/المبيعات التجزئة، وتصبح باسم وظيفي أدق مثل **إعداد موقع التشغيل الأول**. تتضمن اختيار/إنشاء المستودع وربطه بالمركزين الماليين ونقطة البيع عند الحاجة. لا تظهر مطلقاً عند تشغيل المالية أو الموارد البشرية فقط، ولا تبقى بطاقة غامضة في آخر تبويب من تبويبات الهيكل التنظيمي.

### 5. المراجعة، الإطلاق، والانتقال

عند انتهاء المتطلبات الأساسية، تعرض الواجهة ملخصاً قابلاً للتدقيق: ما الذي سيصبح فعالاً، الموارد التي ستنشأ، الوحدات الجاهزة، والوحدات المؤجلة. زر الإطلاق ينفذ عملية خلفية قابلة لإعادة المحاولة ويعرض تقدماً حقيقياً؛ لا يعلن النجاح قبل أن تؤكد الخلفية ذلك.

بعد الإطلاق الأساسي، ينتقل المستخدم إلى وجهة البداية التي تحددها الخلفية. تظهر قائمة جانبية محدودة للنواة والوحدات الجاهزة فقط، ويبقى مركز الإطلاق متاحاً لإكمال الوحدات المؤجلة أو لإضافة وحدة لاحقاً. هذا يحقق الإخفاء قبل التهيئة مع الكشف التدريجي الآمن بعدها.

## تجربة الواجهة: `/setup` ليست صفحة إعدادات

تستخدم الواجهة تخطيطاً مستقلاً عن `MainLayout`. في الأعلى تظهر الهوية، اللغة، المساعدة، وحفظ تلقائي ظاهر للمستخدم. في الجانب يظهر «خريطة الإطلاق» مع حالات الخطوات. وفي المساحة الرئيسة يظهر قرار أو نموذج واحد في كل مرة. يبقى زر الرجوع متاحاً فقط إلى خطوات سابقة لا يسبب تعديلها إبطال مخرجات لاحقة دون تحذير واضح.

| عنصر واجهة التهيئة | السلوك المطلوب |
| --- | --- |
| خريطة الخطوات | تبيّن المنجز، الجاري، المحجوب، والمطلوب لاحقاً؛ لا تسمح بالقفز فوق تبعية غير محققة. |
| حفظ واستئناف | عبارة ثابتة مثل «حُفظت آخر تغييراتك» بعد تأكيد API، لا بمجرد تعديل حقل في المتصفح. تستعاد المسودة من الخلفية بعد التحديث أو إعادة التشغيل. |
| أخطاء الحقول | ملخص أعلى النموذج وروابط إلى الحقول، مع رمز خطأ ثابت ونص إصلاحي مفهوم؛ لا تعرض استثناءات خلفية. |
| التحقق الطويل | شاشة حالة تقدم حقيقية مرتبطة بـ `provisioning run`، تدعم التحديث والمغادرة ثم العودة، مع إجراء إعادة محاولة آمن. |
| العربية والإنجليزية | RTL/LTR، ترتيب بصري معكوس لا منطقي فقط، انتقال تركيز واضح، عناوين دلالية، ورسائل حالة قابلة للقراءة لقارئات الشاشة. |
| الجلسات المتعددة | عند تغير نسخة التهيئة في تبويب آخر، يعرض إشعار «تم تحديث هذه الخطوة» ويعيد جلب الحالة بدل كتابة بيانات قديمة. |

## معمارية الخلفية المقترحة

### المصدر الوحيد للحقيقة

تضاف طبقة تطبيقية تحت `EnterpriseCore/Setup`, ولا يوضع تنسيق سير العمل داخل المتحكمات أو Zustand. هذه الطبقة تستدعي الخدمات الحالية مثل `OrgStructureService` و`OperatingContextService` ومخزون الوحدة/الصلاحيات، ثم تسجل نتيجة كل خطوة وتقرر انتقال الحالة.

لا تحل الجداول الجديدة محل جداول المؤسسة أو الهيكل أو المستودعات أو نقاط البيع؛ تسجل **قرار التهيئة، حالة التنفيذ، ومراجع المخرجات** فقط. وبذلك يبقى نموذج المجال الحالي هو مالك بياناته.

| كيان مقترح | الغرض | حقول محورية |
| --- | --- | --- |
| `setup_installations` | جلسة تهيئة واحدة فعالة لكل نطاق تثبيت/منشأة. | `scope_type`, `scope_key`, `status`, `configuration_version`, `owner_user_id`, `claimed_at`, `base_launched_at`, `completed_at`, `lock_version`. |
| `setup_steps` | حالة كل خطوة من النسخة المعتمدة لمخطط التهيئة. | `installation_id`, `code`, `module_key`, `sequence`, `status`, `schema_version`, `input_snapshot`, `output_refs`, `error_code`, `actor_id`, `started_at`, `completed_at`, `lock_version`. |
| `setup_module_selections` | قرار اختيار الوحدة وحل تبعياتها وحالتها. | `installation_id`, `module_key`, `selection_status`, `provision_status`, `dependency_snapshot`, `destination_key`, `visible_at`. |
| `setup_provisioning_runs` | عملية غير متزامنة قابلة للمراقبة وإعادة المحاولة. | `installation_id`, `module_key`, `idempotency_key`, `status`, `progress`, `job_reference`, `failure_code`, `started_at`, `finished_at`. |
| `setup_audit_events` | سجل تشغيلي غير قابل للتعديل لأحداث التأسيس. | `installation_id`, `event_type`, `actor_id`, `subject_type`, `subject_id`, `metadata`, `occurred_at`. |
| `setup_idempotency_keys` | منع التنفيذ المزدوج في التحديث/التبويبات/إعادة الإرسال. | `scope_key`, `operation`, `idempotency_key`, `request_hash`, `response_snapshot`, `expires_at`. |

يجب أن تكون هوية النطاق صريحة. إن كان النظام أحادي المنشأة حالياً، يبدأ `scope_type = installation` و`scope_key` ثابتاً؛ وعند تفعيل منشأة في المستقبل يصبح النطاق `organization`. لا يجوز استخدام `user_id` بديلاً عن نطاق المنشأة، لأن المستخدم يصف تفضيل سياق عمل فردي وليس الجاهزية المؤسسية.

### حالات التهيئة والانتقال

توجد حالة عليا للتثبيت وحالة مستقلة لكل خطوة/وحدة. يمنع ذلك من ادعاء أن النظام مكتمل لأن خطوة واحدة نجحت، أو من إخفاء سبب فشل وحدة داخل حالة عامة.

| الحالة العليا | المعنى | الوجهة المسموحة |
| --- | --- | --- |
| `not_started` | لم يُطالب بملكية التهيئة بعد. | bootstrap الآمن أو تسجيل الدخول بحسب سياسة النشر. |
| `in_progress` | توجد مسودة صالحة للاستئناف. | `/setup/{current_step}` فقط. |
| `blocked` | توجد تبعية أو صلاحية أو بيانات مطلوبة. | صفحة الخطوة المحجوبة مع إجراء إصلاح. |
| `awaiting_provisioning` | عملية التفعيل تعمل أو تنتظر نتيجة موثقة. | صفحة تقدم التهيئة. |
| `base_ready` | أسس المنشأة صحيحة؛ يسمح بغلاف النظام المحدود. | وجهة النواة ومركز الإطلاق. |
| `ready_for_destination` | وحدة بعينها جاهزة للظهور والاستعمال. | وجهة الوحدة المحددة. |
| `completed` | كل وحدات حزمة الإطلاق المتفق عليها جاهزة. | لوحة البداية العادية. |
| `recovery_required` | فشل قابل للعلاج أو عدم اتساق يتطلب إجراءً مدققاً. | شاشة استعادة واضحة، لا النظام العادي. |

لا تنقل الواجهة الحالة بنفسها. تستدعي الخلفية إجراء مثل `validateAndCompleteStep`; يتحقق الإجراء من التبعيات، يقفل الصف المقصود، ينفذ التغيير داخل المعاملة المناسبة، ويسجل الحدث ثم يعيد لقطة حالة جديدة.

| المسار | الغرض | ملاحظات حماية وعقد |

| `GET /api/v2/setup/status` | لقطة موحدة للحالة، الخطوة التالية، الوحدات، والوجهات المرئية. | متاح فقط لمالك التهيئة أو المصرح له؛ هو العقد الذي تعتمد عليه الواجهة والحراس. |
| `POST /api/v2/setup/bootstrap/claim` | إنشاء مالك التهيئة الأول. | رمز نشر أحادي الاستخدام، rate limit، تدقيق، وقفل نهائي بعد النجاح. |
| `POST /api/v2/setup/claim` | مطالبة مسؤول مصرح له بجلسة قائمة، إن كانت السياسة تسمح. | عملية ذرية مع قفل صف. |
| `PUT /api/v2/setup/steps/{code}` | حفظ مسودة الخطوة. | `If-Match` أو `lock_version`، ومفتاح idempotency. |
| `POST /api/v2/setup/steps/{code}/validate` | تحقق غير مدمر وإرجاع أخطاء حقلية. | لا يتقدم الحالة. |
| `POST /api/v2/setup/steps/{code}/complete` | تثبيت مخرجات خطوة مكتملة. | ترتيب الخطوات والتحقق في الخلفية. |
| `POST /api/v2/setup/modules/resolve` | تحليل اختيار الوحدات والتبعيات والتعارضات. | يعيد blueprint قابلاً للعرض قبل التأكيد. |
| `POST /api/v2/setup/modules/confirm` | حفظ الحزمة المختارة. | ذرية، idempotent، ومدققة. |
| `POST /api/v2/setup/provisioning/{run}/retry` | إعادة محاولة عملية فاشلة بأمان. | يرفض إعادة التنفيذ إذا كانت النتيجة اكتملت بالفعل. |
| `POST /api/v2/setup/launch` | إطلاق الأساس أو الحزمة بعد كل التحقق. | ينقل إلى `base_ready` أو `completed` فقط بعد النتيجة الفعلية. |

تحتفظ واجهات `operating-context/readiness` و`configure` ووحدات الهيكل التنظيمي بوصفها واجهات مجال. لكن تستدعيها **Actions** جديدة من منسق التهيئة. لا تستدعي صفحة `/setup` متحكمات متعددة مباشرة ثم تستنتج النجاح في المتصفح.

### معالجة سياق التشغيل والمتجر

تفصل البنية بين ثلاثة مفاهيم لا ينبغي خلطها:

| المفهوم | موضعه الصحيح | مثال |
| --- | --- | --- |
| هيكل المنشأة | Organization Governance | شركة، فرع، إدارة، وحدة تشغيلية، علاقات السلطة. |
| سياق التشغيل الأولي للمنشأة | مرحلة وحدة مشروطة داخل التهيئة | مستودع أولي ومركز تكلفة/ربح ونقطة بيع عند اختيار تجارة تجزئة. |
| سياق المستخدم الافتراضي | تفضيل/اختيار تشغيلي بعد الإطلاق | اختيار المستخدم لموقعه أو جهازه عند العمل اليومي. |

ينبغي استخراج منطق إنشاء الموارد من `OperatingContextService::configure` إلى إجراءين قابلين لإعادة الاستخدام: إجراء ينشئ/يتحقق من موارد التشغيل، وإجراء يربط السياق بالمالك الصحيح. يحتفظ endpoint الحالي بسلوكه عبر محول توافق، بينما تستخدم التهيئة إجراءً جديداً يربط الناتج بجلسة التهيئة وبنطاق المنشأة، لا بـ`user_id` فقط. هذا ضروري لأن الخدمة الحالية تجعل السياق الافتراضي شخصياً وتقوم بإنشاء مستودع وPOS من نفس النموذج [6].

## حراسة النظام والتنقل التدريجي

### حارس المسار الأمامي

يستبدل منطق الإشعار داخل `MainLayout` بحارس `SetupGate` يقرأ `GET /setup/status` بعد تحقق الجلسة. قواعده بسيطة وحتمية:

1. مسارات `/auth/*` و`/setup/*` لا تدخل في حلقة إعادة توجيه.
2. إذا كانت التهيئة غير مكتملة وطلب المستخدم أي مسار عادي، يعاد إلى الخطوة المسموحة حالياً في `/setup`.
3. إذا كانت الحالة `base_ready`، يسمح فقط بمسارات النواة ومركز الإطلاق والوحدات التي تعيدها الخلفية بحالة `ready_for_destination`.
4. إذا حاول المستخدم مسار وحدة مختارة غير جاهزة، يعاد إلى بطاقة تهيئة تلك الوحدة مع تفسير المتطلب التالي.
5. لا تُعدّ نتيجة مخزنة محلياً نهائية؛ يعاد الجلب عند تحميل الغلاف وعند استجابة تعارض الإصدار.

### حارس الخادم

حارس الواجهة ليس ضماناً أمنياً. تضاف سياسة `EnsureModuleOperational` أو ما يماثلها إلى مجموعات المسارات الحساسة في API. تفحص السياسة، بعد التحقق من الصلاحية، أن الوحدة مفعلة وجاهزة لنطاق المنشأة. لذلك لا ينفع لصق رابط مباشر أو استدعاء API يدوي للوصول إلى وحدة غير مكتملة.

### نموذج الإتاحة للتنقل

لا تعدل ملفات تعريف التنقل الثابتة لتصبح قاعدة الحقيقة. تظل هذه الملفات تعرّف البنية والمظهر، لكن يدمج محول التنقل لقطة `visible_module_keys` و`available_destination_keys` الواردة من `/setup/status` قبل العرض. كما يطبق الفلتر نفسه على القائمة الجانبية وبطاقات `/navigation` والبحث والتنقل المباشر.

| قرار الإظهار | الشرط |
| --- | --- |
| مخفي كلياً | الوحدة لم تُختر، أو اختيرت ولكن لم تُهيأ، أو المستخدم لا يملك الصلاحية. |
| ظاهر في مركز الإطلاق فقط | الوحدة مختارة وتحتاج عملاً أو تنتظر provisioning. |
| ظاهر في القائمة | للمستخدم صلاحية العرض، والوحدة بحالة `ready_for_destination`، والوجهة مسموحة للنطاق. |
| محجوب من API | الوحدة غير مفعلة أو متطلب مؤسسي ناقص، حتى لو امتلك المستخدم صلاحية تقليدية. |

## ما يُنقل وما يبقى في الصفحة الحالية

تظل صفحة الهيكل التنظيمي الحالية مهمة، لكنها لا تكون واجهة التثبيت الأولى. التغيير ليس حذفاً لمحرك الهيكل، بل **إعادة تحديد موضعه في الرحلة**.

| العنصر الحالي | القرار | الموضع الجديد |
| --- | --- | --- |
| تبويبات لوحة البيانات، العقد، الروابط، الأنواع، القواعد، تحليل النطاق، السلامة، سجل التغيير | يبقى كمساحة حوكمة متقدمة. | بعد الإطلاق الأساسي، لمن يملك صلاحية الإدارة. |
| إنشاء الحد الأدنى من العقد والعلاقات | يعاد استخدامه في تجربة موجّهة. | خطوة «بناء الهيكل» داخل `/setup`. |
| التحقق من السلامة والطوبولوجيا | يعاد استخدامه ولا يعرض كأدوات تقنية منفصلة للمستخدم الجديد. | زر «تحقق من الهيكل» مع نتائج قابلة للإصلاح قبل التفعيل. |
| بطاقة جاهزية المتجر ونموذجها المنبثق | تزال من صفحة الهيكل. | خطوة مشروطة باسم «إعداد موقع التشغيل الأول» ضمن الوحدة التجارية المناسبة. |
| إشعار عدم الجاهزية من `MainLayout` | يزال كبديل للبوابة. | `SetupGate` ومركز الإطلاق بعد الإطلاق الأساسي. |

## التوافق مع الخلفية الحالية

يمكن تحقيق التصميم دون إعادة بناء المنظومة الخلفية من الصفر، لأن المشروع يحتوي بالفعل على متحكمات وخدمات للهيكل التنظيمي وسياق التشغيل، ومسارات V2 واضحة؛ لكنها تعمل حالياً بصلاحية `settings` وتفتقر إلى حالة تثبيت عامة [8]. التوافق يتم بالتدرج الآتي:

1. **إضافة لا استبدال:** تنشأ جداول وActions ومتحكمات `setup` جديدة؛ لا تعدل العقود الحالية في المرحلة الأولى.
2. **مُنسِّق لا مكرر:** تستدعي Actions الجديدة الخدمات القائمة ثم تحفظ مراجع المخرجات؛ لا تنشئ جدولاً ثانياً للعقد التنظيمية أو المستودعات.
3. **محول توافق لسياق التشغيل:** يحافظ endpoint الحالي على عمله، وينقل منطق الإنشاء القابل لإعادة الاستخدام تدريجياً إلى طبقة خدمة أو Action مشتركة.
4. **إتاحة محسوبة من الخادم:** يجلب العميل قائمة وحدات/وجهات مرئية من عقد الحالة؛ لا يكون التنقل نفسه مصدر الاستحقاق.
5. **وضع انتقال للبيانات الموجودة:** لا يجوز إجبار بيئة عاملة لديها بيانات على bootstrap جديد. تفحص مهمة ترحيل الأدلة الموجودة وتعيّن حالة `legacy_verified` أو `recovery_required` وفق قواعد معلنة ومراجعة إدارية.

## خطة التنفيذ المرتبة

| الموجة | المخرج | تفاصيل القبول |
| --- | --- | --- |
| 0. قرار معماري | ADR وكتالوج حالات وخريطة تبعيات الوحدات. | اعتماد تعريف `base_ready`، سياسة bootstrap، ونطاق التثبيت قبل بدء migrations. |
| 1. نواة الخلفية | جداول التهيئة، Models، policies، status API، idempotency، audit. | اختبار سباق طلبين وتحديث تبويبين؛ جلسة واحدة فعالة فقط لكل نطاق. |
| 2. تأسيس المنظمة | Actions تستدعي Organization Governance لإنشاء مسودات وتفعيلها. | لا يظهر هيكل مسودة كهيكل نشط؛ تظهر أخطاء السلامة كإرشاد قابل للتنفيذ. |
| 3. كتالوج الوحدات | metadata، resolver، selection API، provisioning runs. | اختبار تبعيات متعدية وتعارضات، وعدم ظهور وحدة قبل نجاح provisioning. |
| 4. واجهة `/setup` | غلاف مستقل، step map، الاستئناف، RTL/LTR، أخطاء وتقدم. | تحديث أو إغلاق أو انقطاع شبكة يعيد المستخدم إلى آخر خطوة مسموحة من الخلفية. |
| 5. البوابة والتنقل | `SetupGate`، فلترة التنقل، حماية المسارات وAPI. | لا يمكن فتح صفحة عادية قبل `base_ready`، ولا وحدة غير جاهزة عبر رابط مباشر. |
| 6. إزالة الالتباس | إزالة بطاقة المتجر من صفحة الهيكل وإبقاء مساحة الإدارة المتقدمة. | يبقى إعداد المتجر مشروطاً بالوحدة، ولا يظهر في المالية/HR فقط. |
| 7. الترحيل والإطلاق | كاشف البيئات القائمة، feature flag، مراقبة، وخطة تراجع. | نشر تجريبي دون منع العملاء القائمين أو تكرار مواردهم. |

## التغطية الاختبارية المطلوبة

| السيناريو | النتيجة المطلوبة |
| --- | --- |
| تثبيت جديد: النواة فقط | لا يعرض الغلاف حتى ملف المنشأة والهيكل الأساسي ثم يسمح بالنواة فقط. |
| تثبيت جديد: مالية | لا يطلب مستودعاً أو POS ما لم تكن الوحدة المختارة تفرضهما. |
| تثبيت جديد: تجزئة + مخزون | يطلب موقع التشغيل بعد اعتماد الهيكل والمراكز اللازمة، ثم يظهر المسار التجاري فقط بعد نجاح السياق. |
| حفظ ثم تحديث/إغلاق | تعود الواجهة إلى الحالة الخلفية وآخر خطوة مسموحة، دون فقد مخرجات مثبتة. |
| تبويبان أو طلبان متزامنان | ينجح طلب واحد أو يعيد الثاني النتيجة المخزنة؛ لا يتكرر مسؤول أو مستودع أو provisioning. |
| رابط عميق لوحدة غير جاهزة | يعاد إلى خطوة التهيئة المناسبة، وتُرفض API الحساسة أيضاً. |
| مستخدم بلا صلاحية | لا يستطيع رؤية تفاصيل التهيئة أو المطالبة بها أو تعديلها. |
| بيئة قائمة | لا يفتح bootstrap؛ تعرض حالة ترحيل/تحقق لا تدمّر بيانات الإنتاج. |
| العربية وLTR | اتجاه، تركيز، قارئ شاشة، ترتيب خطوة وخطأ حقلي صحيح في اللغتين. |

## تعريف الإنجاز

يعد العمل مكتملاً فقط عندما تصبح حالة التهيئة محفوظة في الخلفية وقابلة للاستئناف، وتكون منشأة جديدة غير قادرة على مشاهدة غلاف ERP قبل التأسيس الإلزامي، ويظهر الهيكل التنظيمي المبسّط في التهيئة دون استبدال محرك الحوكمة المتقدم، وتصبح جاهزية المتجر مرحلة مشروطة وليست نموذجاً عاماً، وتظهر كل وحدة في التنقل حصراً بعد تحقق جاهزيتها من الخلفية، وتمنع الحماية الخلفية الوصول المباشر إلى وحدة غير مشغلة.

### مقياس نجاح تشغيلي

| المؤشر | معيار القبول عند الإطلاق |
| --- | --- |
| الوصول المبكر | **صفر** مسار عادي أو API لوحدة غير جاهزة يصل إليه مستخدم جديد عبر رابط مباشر. |
| قابلية الاستئناف | يستعيد المستخدم الخطوة الصحيحة ومخرجاتها المثبتة بعد التحديث أو إغلاق التطبيق أو انقطاع الشبكة. |
| التكرار | لا ينشئ التحديث أو إعادة الإرسال أو التبويبات المتنافسة مسؤولاً أو مستودعاً أو عملية توفير مكررة. |
| دقة الكشف | لا تظهر وحدة في القائمة قبل تحقق الخلفية من `ready_for_destination`. |
| ملاءمة المتطلبات | لا يظهر إعداد المتجر إلا في مخططات تشغيل تتطلبه فعلاً. |
| قابلية الفهم | كل حظر يعرض السبب وإجراء الاستعادة والوجهة التالية، بلا رسائل تقنية خام. |

> **نقطة البدء الموصى بها:** اعتماد ADR والحالة العليا أولاً، ثم تنفيذ Status API وجداول التهيئة قبل أي واجهة أو تعديل للقائمة. البدء بـwizard في الواجهة قبل هذا الأساس سيعيد إنتاج المشكلة الحالية: تجربة جميلة ظاهرياً لكن غير موثوقة عند التحديث أو التزامن أو الوصول المباشر.
